# Процесс разработки

Обязательная основа для агента. Пользователь не пишет код: он ставит задачу голосом или текстом и проверяет результат в игре. Агент сам изучает игру, собирает мод и проверяет его.

## Исследование игры

- **DEV-01. Пронумерованные документы.** Всё, что агент узнал об игре, записывается в папку `docs/` проекта: `00_capabilities.md`, `01_overview.md`, `02_engine.md`, `03_saves.md`, `04_input.md` и далее по темам; заготовки — `templates/docs/`. Новый агент или новый чат продолжает с них, а не изучает игру заново. Порядок работы — [исследование](research.md).
- **DEV-02. «Проверено» и «выведено».** Каждое утверждение помечено `[V]` — проверено в игре, `[I]` — выведено из кода или названий, не проверено, или `[W]` — взято из сети или у сообщества, на этой игре не проверено. Перед тем как обещать функцию пользователю, `[I]` и `[W]` проверяются.
- **DEV-03. Опасные клавиши.** Отдельным списком — встроенные отладочные клавиши и команды разработчиков, которые могут сломать сейв или сцену, и клавиши самой игры. Этот список адаптер использует для проверки конфликтов хоткеев.
- **DEV-04. Новый билд.** После обновления игры агент сравнивает сборку с предыдущей и пишет короткий отчёт: что пропало, переименовалось или изменилось из того, на что опирается мод. Затем запускает самопроверку (CORE-22).
- **DEV-11. Журнал и стоп-кран.** `MODLOG.md` ведётся после каждого значимого шага: что сделано, результат, следующее. Одна и та же ошибка трижды — остановиться, записать известное, сменить подход или спросить пользователя.
- **DEV-12. Маршрут до работы.** В `MODDING_PLAN.md` до первого патча записаны стек (из `scripts/recon.py`), выбранный маршрут и причина. Порядок выбора — от дешёвого к дорогому, [исследование](research.md), шаг 4.
- **DEV-13. Декомпиляция вне проекта.** Декомпилированный код, дампы и interop-сборки лежат вне папки проекта и репозитория и не публикуются. В `docs/` попадают выводы и имена, а не листинги.
- **DEV-14. Карточка игры.** `docs/knowledge.md` по [шаблону](../templates/docs/knowledge-card.md): версии игры, движка и загрузчика, маршрут, что работает и Gotchas «симптом → причина → решение». Её читает первым следующий агент. Общая грабля предлагается пользователю для [pitfalls.md](pitfalls.md).

## Инструменты агента

- **DEV-05. Цикл одной командой.** Скрипт «собрать мод → закрыть игру → установить → запустить → дождаться уровня». Агент не собирает этот путь вручную каждый раз. Заготовка — `templates/tools/dev_cycle.py` с путями в одном `paths.json`. Игру, в которой сидит пользователь, цикл закрывает и перезапускает только с его согласия: спросить до запуска, а не после.
- **DEV-06. Автоснимок вокруг пересборки.** Перед закрытием игры для пересборки хелпер снимает служебный снимок текущей сцены (при подключённых сохранениях — с рецептом), после запуска загружает его обратно. Пользователь после пересборки оказывается там же, где был. Служебные снимки не засоряют пользовательскую галерею.
- **DEV-07. Ввод изнутри.** Внутренняя команда адаптера «нажать хоткей / нажать кнопку интерфейса игры», доступная агенту для проверки. Windows не даёт фоновому процессу посылать клавиши в чужое окно, поэтому ввод имитируется внутри игры. Пользователю эта команда в панели не показывается.
- **DEV-08. Список «проверить руками».** То, что агент проверить не смог (ощущение управления, геймпад, звук, редкие сцены), отдельным коротким списком, а не россыпью оговорок по тексту. Полный список живёт в одном файле проекта `docs/CHECKS.md` и дополняется; в отчёт идёт выжимка из него, новый список в каждом отчёте не заводится.
- **DEV-15. Доступ в живую игру.** Включаемые настройкой служебные команды плагина `inspect.*` и `log.tail` позволяют агенту искать объекты, читать и менять поля и вызывать методы без пересборки. Пользователю в панели не показываются и по умолчанию выключены; при распространении проверяется, что настройка выключена.
- **DEV-17. Команда проверки на каждую функцию.** Вместе с новой функцией появляется служебная команда, которой агент запускает её и читает результат числом или состоянием. Клавиши игры агент нажимать не может (DEV-07): функция, которую нечем вызвать, остаётся непроверенной.
- **DEV-18. Договор до кода.** Команды новой функции — имена, аргументы, ответ, поля состояния — записываются в документ протокола проекта до того, как пишутся плагин, сервис и страница. Части делаются порознь и сверяются с одним текстом.
- **DEV-19. Игру трогает один агент.** Запущенная игра одна: собирать, перезапускать и проверять в ней в один момент может только один агент. Остальные работают без игры — сайт, сервис, документы; имитация игры для них — возможность, а не обязанность.

## Предложения после изучения игры

- **DEV-09. Ничего лишнего по умолчанию.** Изучив игру, агент даёт пользователю короткий список того, что в ней реально доступно сверх заказанного: управление ИИ (убрать NPC, невидимость для врагов), спавн объектов и персонажей, открытие экранов игры (инвентарь, карта, диалог по id). По каждому пункту — одна строка: что даёт и насколько надёжно. Без выбора пользователя ничего из этого не делается. Предложения модулей записаны в их ТЗ, раздел «Предложить до съёмок», и показываются, только если модуль выбран. Общие для любой игры с интерфейсом и сменой дня и ночи: скрытие интерфейса по слоям и заморозка времени суток. Свет для съёмки, скорость игрока и плавность мыши от первого лица — только по отдельному заказу ([паттерны](optional-patterns.md)).
- **DEV-10. Справочник и постановка — по смыслу игры.** Модуль «Справочник» предлагается, если читы работают с предметами или сущностями по id; «Постановка» — если в мире есть что-то движущееся само. В остальных играх их не предлагать.
- **DEV-16. Цена служебных возможностей — после разведки.** До начала сборки агент называет пользователю цену управления из чата и служебного доступа в игру для этой игры по таблице в `modules/mcp/SPEC.md`: «готово из шаблона», «порт, около половины дня», «отдельное исследование». Это оценка; дорогой вариант не делается без согласия.

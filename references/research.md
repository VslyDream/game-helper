# Исследование игры и мод

Этап 1 работы. Цель хелпера — снимать игру для трейлеров и роликов: чистый кадр, свободная камера, управление временем, погодой и ИИ, повторяемые дубли. Поэтому исследование отвечает на вопрос «что из этого игра позволяет и какой ценой», а не «как взломать всё».

## Цикл

1. **Заявка.** Игра, папка, режимы (соло/хост/клиент), заказанные функции. Онлайн-игры с античитом (EAC, BattlEye и т. п.) — вне рамок: остановиться и спросить пользователя.
2. **Разведка.** `python scripts/recon.py "<папка игры>" --out <проект>/docs/MODDING_PLAN.md`. Скрипт только читает папку игры: движок, Mono/IL2CPP, версии Unity и метаданных, загрузчики, библиотеки, путь к логам, Steam appid, античит. По результату открыть **один** плейбук из [engines/](engines/README.md).
3. **Знания.** Если у игры уже есть `docs/knowledge.md` (карточка из [шаблона](../templates/docs/knowledge-card.md)) — прочитать её и раздел Gotchas до любых действий. Общие грабли — [pitfalls.md](pitfalls.md), только нужные разделы.
4. **Маршрут.** Выбрать самый дешёвый рабочий путь и записать его с причиной в `MODDING_PLAN.md` до начала работы: штатные средства игры (консоль, дебаг-меню, фоторежим) → данные и ассеты (конфиги, ScriptableObject) → патч управляемого кода (Harmony) → нативный хук. Следующий уровень — только когда предыдущий не даёт нужного.
5. **Лаборатория.** Работать на копии игры или с бэкапом сейвов (CORE-20), в одноразовом слоте. Загрузчик закрепить по версии/номеру сборки и записать в `docs/02_engine.md` вместе со способом его отключить.
6. **Чтение кода.** Декомпиляция и дампы — вне папки проекта и репозитория, никогда не публикуются. Искать по [шпаргалке](engines/unity-where-to-look.md) и записывать находки в `docs/05_systems.md` с пометками `[V]`/`[I]`.
7. **Матрица возможностей.** Заполнить `docs/00_capabilities.md`: что есть в игре для съёмки, где оно, проверено ли, насколько надёжно. Из неё — короткий список предложений сверх заказанного (DEV-09).
8. **Вертикальный срез.** Первая функция сквозь всю цепочку: плагин → локальный API → панель → подтверждённый результат в игре. Только после этого — остальные читы. Каркас плагина — [templates/plugin-il2cpp/](../templates/plugin-il2cpp/README.md), цикл сборки — [templates/tools/](../templates/tools/README.md).
9. **Оракул — живая игра.** Готово — это лог без ошибок плюс скриншот, который агент действительно посмотрел (уменьшенный для экономии), и повторяемый способ проверки (команда API или хоткей). Сборка без ошибок — не проверка.
10. **Запись знаний.** После каждого значимого шага — запись в `MODLOG.md`; находки — в нумерованные `docs/`; новая грабля — в Gotchas карточки игры, а если она общая — предложить пользователю добавить её в `references/pitfalls.md` этого набора.

## Правила

- **MODLOG.** Всё, чего нет в `MODLOG.md`, теряется при сжатии контекста или смене чата. Запись после каждого значимого шага: что сделал, результат, следующий шаг.
- **Стоп-кран.** Одна и та же ошибка три раза подряд — остановиться, записать известное в `MODLOG.md`, сменить подход или спросить пользователя. Не перебирать вслепую.
- **Не угадывать.** Утверждение `[I]` проверяется в игре, прежде чем обещать функцию пользователю.
- **Инструменты — CLI.** Агент не кликает GUI: ilspycmd, Cpp2IL, UnityPy, rg, локальный API плагина. UnityExplorer и ConfigurationManager — удобство для человека, не основной путь агента.
- **Доступ агента в живую игру.** В плагине включаемые настройкой служебные команды `inspect.*` и `log.tail` (см. шаблон плагина): найти объект, прочитать/изменить поле, вызвать метод, не пересобирая мод. В панели пользователя они не показываются.

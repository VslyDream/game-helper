# Управление из чата (MCP)

Подключаемый модуль без своей страницы. Агент в чате управляет игрой теми же командами, что и панель: пользователь диктует «загрузи такой-то момент, включи бессмертие, давай ещё раз», агент выполняет и показывает кадр.

## Поведение

- **MCP-01. Одни команды на двоих.** MCP-сервер не дублирует логику: он вызывает тот же локальный API (`/api/action`, `/api/state`), что и сайт. Новая команда адаптера сразу доступна и в панели, и в чате.
- **MCP-02. Без перезапуска.** Список инструментов MCP строится из `GET /api/commands` адаптера. Добавленный чит или команда появляются у агента после пересборки мода, без перезапуска MCP-сервера и чата. Если клиент MCP кеширует список, есть общий инструмент `run {command,args}` и `commands` (список с описаниями), чтобы новая команда была доступна сразу.
- **MCP-03. Кадр в чат.** Инструмент `screenshot` возвращает текущий кадр игры картинкой, по желанию уменьшенный. Агент проверяет им результат, прежде чем сказать «готово».
- **MCP-04. Ожидание готовности.** `wait_ready {timeout}` ждёт, пока игра запустится, загрузит уровень или закончит операцию. Агент не гадает паузами.
- **MCP-05. Пауза видна всегда.** В каждом ответе инструментов есть короткая строка состояния: подключение, сцена, пауза и скорость времени. Так агент не путает «игра зависла» с «стоит на паузе».
- **MCP-06. Описания для голоса.** Описание каждой команды и чита — обычными словами, с синонимами, которыми пользователь может её назвать («скрыть интерфейс», «убрать HUD»). При подключённом справочнике агент ищет id по нему, а не перебирает игру заново.
- **MCP-07. Те же ограничения.** Команда, недоступная в панели, недоступна и в чате, с той же причиной. Агент не обходит недоступность прямыми вызовами.

## `GET /api/commands`

```json
[
  {"command": "cheat.set", "id": "hideUi", "title": "Скрыть интерфейс игры",
   "aliases": ["убрать HUD", "чистый кадр"], "args": {"value": "boolean"}},
  {"command": "snapshots.retake", "title": "Дубль заново",
   "aliases": ["давай ещё раз", "перезагрузи сцену"], "args": {}},
  {"command": "inspect.find", "title": "Найти объекты в сцене",
   "args": {"type": "string?", "name": "string?", "limit": "number?"}, "dev": true}
]
```

Список отдаёт адаптер из своего реестра: по записи на каждый чит (`cheat.set` для переключателей и значений, `cheat.run` для действий, с `id`) и по записи на каждую команду модулей. Доступность берётся из `state.availability`. Служебные команды помечены `"dev": true` и в `availability` не входят (MCP-09).

## Служебный доступ агента в игру (режим разработки)

Это не функция для пользователя, а инструмент агента на время изучения игры и отладки: проверить догадку в запущенной игре за секунды вместо цикла «пересобрать мод → перезапустить игру → дойти до уровня».

- **MCP-08. Что получает агент.** Ровно то, что реализует адаптер. В каркасе Unity IL2CPP (в наборе — `templates/plugin-il2cpp/src/Inspect.cs`, в проекте — `adapter/src/Inspect.cs`):

  | Команда | Что делает |
  |---|---|
  | `inspect.types {query}` | найти тип игры по части имени |
  | `inspect.find {type?, name?, limit?, assets?}` | найти объекты в загруженных сценах по типу компонента и/или имени |
  | `inspect.get {target, path?, depth?, methods?}` | прочитать объект, поле, элемент списка, статические члены типа; по `methods` — список методов |
  | `inspect.set {target, path, value}` | записать поле или свойство: число, строка, bool, enum, простая структура |
  | `inspect.invoke {target, path?, method, args?}` | вызвать метод с простыми аргументами |
  | `log.tail {n?, grep?}` | хвост журнала загрузчика |

  `target`: `obj:<id>` из прошлого ответа, `go:<имя объекта>`, `type:<Тип>`. Отдельной команды «наблюдать значение» нет: агент повторяет `inspect.get` или ставит временный хук с записью в журнал. Не поддерживаются generic-методы, `ref/out`, делегаты и объекты игры в аргументах; чтение свойства вызывает геттер игры.
- **MCP-09. Только разработка.** Команды регистрируются при `[Dev] DevTools = true` в конфиге плагина (по умолчанию выключено). В панели их нет, в `state.availability` они не попадают, в `GET /api/commands` помечены `"dev": true`. MCP-сервер пользователя такие записи пропускает, если не запущен с явным флагом разработки. В сборке для пользователя флаг выключен; при распространении проверить это (а лучше исключить файл из сборки).
- **MCP-10. MCP-сервер для этого не нужен.** Агенту-разработчику хватает CLI проекта `tools/helper_cli.py` (в наборе — `templates/tools/helper_cli.py`): `inspect … | log | shot | wait` — он ходит в тот же `/api/action`. MCP-сервер нужен пользователю для управления из чата (MCP-01…07); служебный доступ работает и без выбранного модуля MCP.
- **MCP-11. Бережный расход контекста.** Ответы ограничены адаптером: `types` — до 100 строк, `find` — 30 объектов по умолчанию (до 200), коллекции — 50 элементов, объект — до 150 членов, `depth` 1 по умолчанию (до 3), `log.tail` — 100 строк (до 1000). Общего лимита на размер ответа нет, поэтому агент сужает сам: сначала `find` с малым `limit`, затем `get` с точным `path` и `depth` 0–1; `depth` 2–3 и `methods` — только на конкретном объекте. CLI и MCP-сервер заменяют полный `state` в ответе одной строкой состояния (MCP-05).
- **MCP-12. Осторожность.** `inspect.set` и `inspect.invoke` меняют живую игру мимо проверок доступности и могут её уронить или испортить сохранение — только на копии или профиле для разработки (DEV-13). Найденное рабочее решение переносится в обычную команду адаптера; пользовательская функция не должна зависеть от `inspect.*`.

### Цена по движкам

Оценка до изучения игры; точную цену агент называет после разведки (обфускация, версия загрузчика, античит её меняют).

| Игра | Служебный доступ агента | Управление из чата (MCP-сервер) |
|---|---|---|
| Unity IL2CPP + BepInEx 6 | Готово из шаблона: включить настройку. На первой игре — короткая проверка трёх помеченных мест каркаса (до часа работы агента). Обфусцированные имена полей остаются нечитаемыми. | Адаптерная часть (`/api/commands`, кадр, состояние) готова в каркасе. Сам сервер — тонкая обёртка над API, пишется один раз (пара часов работы агента), дальше общий для всех движков. |
| Unity Mono + BepInEx 5 | Каркаса плагина для Mono нет: переносится весь (API, очередь главного потока, JSON — `System.Text.Json` в Mono-играх обычно нет). `Inspect` при переносе упрощается: обычная рефлексия без interop-обёрток. Вместе с каркасом — около половины дня работы агента один раз, потом переиспользуется. Нужда меньше: код игры читается целиком, есть горячая перезагрузка плагина (ScriptEngine). | То же, что выше, после переноса каркаса. |
| Unreal + UE4SS (Lua) | Штатно в Lua есть поиск объектов (`FindFirstOf`, `FindAllOf`, `StaticFindObject`), чтение и запись свойств, вызов функций, видимых системе отражения движка, и горячая перезагрузка скриптов. Готовых команд `inspect.*` и HTTP нет: нужна служебная команда «выполнить фрагмент Lua в игровом потоке» поверх связи мода с сервисом — от пары часов до половины дня. Поля и функции C++ без отражения недоступны; массивы структур в сетевых обработчиках читать опасно. | Сервер тот же, но ходит в сервис панели (он переводит запросы в связь с модом); список команд и кадр нужно сделать на стороне мода или сервиса — отдельная работа. |
| Прочее (Godot, свой движок, нативный код, игра с античитом) | Отдельное исследование без гарантии. Запасной путь: журнал, снимок экрана и обычный цикл пересборки. | Возможно, только если уже есть адаптер с локальным API. |

## Приёмка

1. Новый чит, добавленный в адаптер, вызывается из чата без перезапуска MCP-сервера.
2. `screenshot` и `wait_ready` работают при закрытой игре, в меню и на уровне, с понятным ответом в каждом случае.
3. Ответ при паузе и скорости ×0 прямо говорит об этом.
4. При выключенной настройке разработки `inspect.*` и `log.tail` отвечают «Команда не поддерживается», их нет в `GET /api/commands` и в инструментах MCP.
